# Лаборатори №6: Тест тохиолдол боловсруулах — Category-Partition ба PICT

**Хичээл:** F.CSA313 — Программ хангамжийн чанарын баталгаа ба тест (2026)

**Оюутны нэр:** С.Тэргэл

**Оюутны код:** B232270011 

**Үйлдлийн систем:** Arch Linux

**Тестийн хэрэгсэл:** Microsoft PICT

**Зорилго:** Category-Partition аргаар тестийн сонголт, төлөөлөх утга, хязгаарлалт, спецификацийн хүснэгт боловсруулах, мөн PICT ашиглан pairwise болон 3-way тестийн багц үүсгэж харьцуулах.

# Хэсэг A. Category-Partition аргаар тест дизайн хийх

## A1. Сонголт ба төлөөлөх утгууд

Тестлэх функц нь `POST /transfer` хүсэлтээр нэг данснаас нөгөө данс руу мөнгө шилжүүлнэ.

```json
{
  "from": "ACC001",
  "to": "ACC002",
  "amount": 10000,
  "currency": "MNT"
}
```

Функцийн үндсэн дүрмүүд:

* Шилжүүлэгч данс (`from`) байгаа, царцаагаагүй байх ёстой.
* Хүлээн авагч данс (`to`) байгаа бөгөөд `from`-оос өөр байх ёстой.
* `amount > 0` байх ёстой.
* Шилжүүлэх дүн нь дансны үлдэгдэл болон өдрийн лимитээс хэтрэхгүй байх ёстой.
* Валют өөр бол ханшийн хөрвүүлэлт хийнэ.
* Үлдэгдэл болон лимитийг хөрвүүлсний дараах дүнгээр шалгана.

### Сонголт ба утгын хүснэгт

| Параметр | Сонголт     | Төлөөлөх утга                                 |
| -------- | ----------- | --------------------------------------------- |
| From     | Valid       | Байгаа, царцаагаагүй данс                     |
| From     | Frozen      | Байгаа боловч царцаасан данс                  |
| From     | Missing     | Байхгүй дансны ID                             |
| To       | Valid       | Байгаа, `from`-оос өөр данс                   |
| To       | Missing     | Байхгүй дансны ID                             |
| To       | SameAsFrom  | `from`-той ижил дансны ID                     |
| Amount   | Normal      | Эерэг, үлдэгдэл ба лимитэд багтах дүн         |
| Amount   | Zero        | 0 буюу тэг дүн                                |
| Amount   | OverBalance | Үлдэгдлээс их дүн                             |
| Amount   | OverLimit   | Өдрийн лимитээс хэтэрсэн дүн                  |
| Currency | Same        | Дансны валюттай ижил валют                    |
| Currency | Different   | Дансны валютаас өөр, хөрвүүлэлт шаардах валют |

### Далд орчны сонголтууд

Функцийн орчинд дараах нөхцөлүүд үр дүнд нөлөөлнө:

1. Данс байгаа эсэх.
2. Данс царцаасан эсэх.
3. Шилжүүлэгч дансны үлдэгдэл.
4. Өдрийн лимитийн нийт хэмжээ болон өмнө ашигласан дүн.
5. Дансны үндсэн валют.
6. Валютын хөрвүүлэлтийн ханш.

Эдгээрийг тестийн `setup` хэсэгт тодорхойлж өгнө. Жишээлбэл, `OverBalance` тест хийхэд дансны үлдэгдлийг 50,000₮, шилжүүлэх дүнг 60,000₮ байхаар тохируулна.

## A2. Хязгаарлалт ба тооцоолол

Энэ лабораторид `[ERROR]` нь алдааны нөхцөлийг, `[SINGLE]` нь тухайн нөхцөлийг бусад нөхцөл хэвийн үед тусгаарлан шалгах сонголтыг, `[IF/property]` нь сонголтуудын хоорондын хамаарлыг илэрхийлнэ. `[SINGLE]` тестэд нэг параметрийн утгыг өөрчилж, бусад параметр болон орчны нөхцөлийг хэвийн тогтмол байлгана.

| Сонголт                          | Тэмдэглэгээ     | Үндэслэл                                                        |
| -------------------------------- | --------------- | --------------------------------------------------------------- |
| From = Valid                     | `[SINGLE]`      | Шилжүүлэгч данс хэвийн байх үндсэн нөхцөл.                      |
| From = Frozen                    | `[ERROR]`       | Царцаасан дансны алдааг тусгаарлан шалгана.                     |
| From = Missing                   | `[ERROR]`       | Байхгүй шилжүүлэгч дансны алдааг шалгана.                       |
| To = Valid                       | `[SINGLE]`      | Хүчинтэй хүлээн авагчтай үеийн үндсэн нөхцөл.                   |
| To = Missing                     | `[ERROR]`       | Байхгүй хүлээн авагчийн алдааг шалгана.                         |
| To = SameAsFrom                  | `[ERROR]`       | Ижил данс руу шилжүүлэхийг хориглох нөхцөл.                     |
| Amount = Normal                  | `[SINGLE]`      | Зөв дүнтэй үндсэн шилжүүлгийг шалгана.                          |
| Amount = Zero                    | `[ERROR]`       | `amount ≤ 0` алдааг шалгана.                                    |
| Amount = OverBalance             | `[ERROR]`       | Үлдэгдэл хүрэлцэхгүй алдааг шалгана.                            |
| Amount = OverLimit               | `[ERROR]`       | Өдрийн лимит хэтрэх алдааг шалгана.                             |
| Currency = Same                  | `[SINGLE]`      | Валют хөрвүүлэлтгүй шилжүүлгийг шалгана.                        |
| Currency = Different             | `[IF/property]` | Валют өөр үед хөрвүүлэлт хийж, хөрвүүлсэн дүнг шалгана.         |
| From = Missing → Amount = Normal | `[IF/property]` | Байхгүй дансны алдааг буруу дүнгийн алдаатай холихгүй.          |
| To = Missing → Amount = Normal   | `[IF/property]` | Байхгүй хүлээн авагчийн алдааг буруу дүнгийн алдаатай холихгүй. |

### Хязгаарын утгатай SINGLE спецификаци

`Amount = Normal` сонголтыг зөвхөн нэг ерөнхий утгаар шалгах нь хязгаарын алдааг илрүүлэхэд хангалтгүй. Иймээс бусад нөхцөлийг хэвийн тогтмол байлгаж, нэг удаад зөвхөн дүнгийн утгыг өөрчилнө. Доорх тоонууд нь лабораторийн жишээний setup бөгөөд API-ийн бодит бизнесийн дүрэмд нийцэж буйг сервер дээр тусад нь баталгаажуулах шаардлагатай.

| ID | Setup | Amount | Хүлээгдэх үр дүн |
| -- | ----- | -----: | ---------------- |
| SINGLE-01 | Хүчинтэй дансууд; үлдэгдэл 150,000₮; лимитийн үлдэгдэл 200,000₮ | 0₮ | `ERROR_BAD_AMOUNT` |
| SINGLE-02 | Хүчинтэй дансууд; үлдэгдэл 150,000₮; лимитийн үлдэгдэл 200,000₮ | 1₮ | Амжилттай шилжүүлэг |
| SINGLE-03 | Хүчинтэй дансууд; үлдэгдэл 150,000₮; лимитийн үлдэгдэл 200,000₮ | 150,000₮ | Амжилттай шилжүүлэг — үлдэгдлийн яг хязгаар |
| SINGLE-04 | Хүчинтэй дансууд; үлдэгдэл 150,000₮; лимитийн үлдэгдэл 200,000₮ | 150,001₮ | `ERROR_INSUFFICIENT` |
| SINGLE-05 | Хүчинтэй дансууд; үлдэгдэл 200,000₮; лимитийн үлдэгдэл 100,000₮ | 100,000₮ | Амжилттай шилжүүлэг — лимитийн яг хязгаар |
| SINGLE-06 | Хүчинтэй дансууд; үлдэгдэл 200,000₮; лимитийн үлдэгдэл 100,000₮ | 100,001₮ | `ERROR_LIMIT` |

Энэ нь `SINGLE` зарчмаар хязгаарын утгыг шалгаж буй жишээ: нэг тестэд дүнгийн утгыг л өөрчилж, бусад нөхцөлийг хэвийн байлгана. Хязгаарын яг тэнцүү утгыг зөвшөөрнө гэж үзсэн; хэрэв системийн шаардлагад өөрөөр заасан бол oracle-ийг шаардлагад нийцүүлэн өөрчилнө.

### Бүрэн олонлогийн тоо

From сонголт 3, To сонголт 3, Amount сонголт 4, Currency сонголт 2 утгатай.

Бүрэн боломжит хослолын тоо:

$$
N=3\times3\times4\times2=72
$$

Хоёр `IF` хязгаарлалтыг тооцъё.

* `From = Missing` үед `Amount` зөвхөн `Normal` байна.
* `To = Missing` үед `Amount` зөвхөн `Normal` байна.
* `From = Missing` болон `To = Missing` давхцсан тохиолдлыг нэг удаа тооцно.

Хязгаарлалтад нийцэх дансны сонголтын хосын тоо:

$$
3+3-1=5
$$

Эдгээр хос бүрд Amount-ийн 4 утгаас зөвхөн 1 нь боломжтой тул хасагдах хослолын тоо:

$$
(4-1)\times2\times5=30
$$

Иймээс:

$$
\boxed{72\rightarrow42}
$$

Энэ тооцоолол нь зөвхөн дээр дурдсан хоёр `IF` хязгаарлалтыг ашигласан үр дүн юм.

### Олон алдааны давуу эрэмбэ

Тодорхойлолтод нэг хүсэлтэд олон алдаа гарвал аль алдааг буцаахыг заагаагүй. Иймээс тестийн oracle боловсруулахдаа дараах таамагласан эрэмбийг хэрэглэнэ:

1. `ERROR_NO_FROM`
2. `ERROR_FROZEN`
3. `ERROR_NO_TO`
4. `ERROR_SAME_ACCOUNT`
5. `ERROR_BAD_AMOUNT`
6. `ERROR_INSUFFICIENT`
7. `ERROR_LIMIT`

Энэ эрэмбийг дансны оршин байгаа эсэх болон царцаалтын шалгалтыг эхэлж, дараа нь хүлээн авагчийн шалгалт, эцэст нь дүнгийн шалгалтыг хийхээр сонгосон бөгөөд тодорхойлолтод давуу эрэмбэ заагаагүй тул энэ нь баталгаажсан бизнесийн дүрэм бус, тестийн oracle-д зориулсан таамаглал юм. Давхар алдаатай тестийн хүлээгдэх үр дүнг энэхүү дарааллаар тодорхойлно.

Эдгээр үр дүн нь үлдэгдэл болон лимитийн яг хязгаарыг зөвшөөрнө гэсэн таамаглалд тулгуурласан. Хэрэв бодит API-ийн шаардлага өөр бол хүлээгдэх үр дүнг тухайн шаардлагаар шинэчилнэ.

Валют өөр үед ханшийн хөрвүүлэлт хийсний дараах дүн нь дансны үлдэгдэл болон өдрийн лимитэд багтах ёстой.

# Хэсэг B. Microsoft PICT ашиглан pairwise тест үүсгэх

## B1. Browser моделийн үр дүн

Browser моделийн параметрүүд:

* Content: Allow, Restrict, Block
* Cookies: Allow, Restrict, Block
* Popups: Yes, No
* Addons: Yes, No
* Attacks: Yes, No
* Forgeries: Yes, No

Бүрэн олонлогийн тоо:

$$
3\times3\times2\times2\times2\times2=144
$$

### Бодит үр дүн

| Арга          | Тестийн мөрийн тоо |
| ------------- | -----------------: |
| PICT 2-way    |                 10 |
| PICT 3-way    |                 20 |
| Бүрэн олонлог |                144 |

2-way PICT үр дүнд 10 мөр гарсан. Лекц дээр гараар 9 мөрөнд багтаасан жишээтэй харьцуулахад PICT нэгээр олон тест үүсгэсэн. Учир нь PICT greedy алгоритм ашигладаг бөгөөд хамгийн цөөн мөртэй багцыг заавал олох баталгаа өгдөггүй.

3-way тест нь параметрийн утгуудын гурвалсан хослолуудыг хамруулах шаардлагатай тул 20 мөр гарсан. Энэ нь бүрэн 144 хослолыг туршихаас цөөн боловч 2-way-аас илүү өргөн хамралттай.

Үр дүнгийн файлууд:

* `results/browser-2way.txt`
* `results/browser-3way.txt`

## B2. Transfer моделийн үр дүн

### Хязгаарлалтгүй модель — `transfer-nc.model`

```text
From: Valid, Frozen, Missing
To: Valid, Missing, SameAsFrom
Amount: Normal, Zero, OverBalance, OverLimit
Currency: Same, Different
```

Энэ моделд `IF` хязгаарлалт байхгүй. Тиймээс алдааны нөхцөлүүд нэг мөрөнд давхардаж болно.

### Хязгаарлалттай модель — `transfer.model`

```text
From: Valid, Frozen, Missing
To: Valid, Missing, SameAsFrom
Amount: Normal, Zero, OverBalance, OverLimit
Currency: Same, Different

IF [From] = "Missing" THEN [Amount] = "Normal";
IF [To] = "Missing" THEN [Amount] = "Normal";
```

Энэ моделд байхгүй дансны алдааг буруу дүнгийн алдаатай хослуулахгүй байх хоёр хязгаарлалт орсон.

### Сөрөг утгатай модель — `transfer-neg.model`

```text
From: Valid, ~Frozen, ~Missing
To: Valid, ~Missing, ~SameAsFrom
Amount: Normal, ~Zero, ~OverBalance, ~OverLimit
Currency: Same, Different
```

PICT-ийн `~` тэмдэглэгээ нь утгыг сөрөг утга гэж тодорхойлно. Ингэснээр нэг тестийн мөрөнд олон сөрөг утга зэрэг орохоос сэргийлж, алдааны нөхцөлүүдийг тусгаарлан шалгах боломжтой.

### Мөрийн тоо ба нэг мөр дэх алдааны нөхцөлийн харьцуулалт

Энд `From = Frozen/Missing`, `To = Missing/SameAsFrom`, `Amount = Zero/OverBalance/OverLimit` тус бүрийг нэг алдааны нөхцөл гэж тоолсон. `Currency = Different` нь дангаараа алдаа биш. `transfer-neg.model`-ийн хувьд `~`-тэй нэг утгыг нэг сөрөг нөхцөл гэж тоолно.

| Модель | Тестийн мөр | Happy path / 0 алдаа | 1 алдаа | 2 алдаа | 3 алдаа |
| --- | ---: | ---: | ---: | ---: | ---: |
| `transfer-nc.model` | 13 | 0 | 3 | 6 | 4 |
| `transfer.model` | 13 | 0 | 4 | 8 | 1 |
| `transfer-neg.model` | 16 | 2 | 14 | 0 | 0 |

`transfer-nc.model` болон `transfer.model` хоёулаа 13 мөр үүсгэсэн ч мөр бүрийн утга болон алдааны нөхцөлийн тархалт өөр байна. Мөрийн тоо ижил байх нь хязгаарлалт нөлөөгүй гэсэн үг биш.

`transfer-neg.model` 16 мөр үүсгэсэн. Эхний хоёр өгөгдлийн мөр нь `Valid, Valid, Normal, Same` болон `Valid, Valid, Normal, Different` бөгөөд `~` тэмдэглэгээгүй учраас загварын түвшинд хоёр эерэг хувилбар байна. Харин үлдсэн 14 мөр тус бүр яг нэг `~` тэмдэглэгээтэй сөрөг утга агуулж байна. `Different` валютын хувилбарын бодит амжилт нь ханшийн хөрвүүлэлт болон дансны нөхцөлөөс хамаарна.

### `~` тэмдэглэгээ ба A2-ын хязгаарлалт

PICT-ийн `~` тэмдэглэгээ нь тухайн утгыг сөрөг утга гэж тэмдэглэдэг болохоос A2 дахь `IF` хязгаарлалтыг автоматаар орлохгүй. Хэрэв загварт дансны байхгүй төлөв болон дүнгийн утгын хооронд бизнесийн хамаарал тавих шаардлагатай бол тэр хамаарлыг `IF` хязгаарлалтаар тусад нь илэрхийлнэ. Харин `transfer-neg.model`-ийн зорилго нь нэг удаад нэг сөрөг нөхцөлийг тусгаарлан шалгах тул `~` утгуудыг хэрэглэсэн бөгөөд өгөгдсөн бодит гаралтад мөр бүрт нэгээс олон `~` алга. Энэ нь бүх боломжит моделд `~` дангаараа заавал нэг сөрөг утгатай мөр үүсгэнэ гэсэн баталгаа биш; гаралтыг шалгаж баталгаажуулах хэрэгтэй.

### PICT гаралтаас гаргасан бодит тест кейсүүд

#### TC-01: Амжилттай шилжүүлэг

**Setup**

* `ACC001` данс байгаа, царцаагаагүй.
* `ACC001` дансны үлдэгдэл 500,000₮.
* `ACC002` данс байгаа бөгөөд `ACC001`-ээс өөр.
* Өдрийн лимитийн үлдсэн хэмжээ 100,000₮.

```json
  "from": "ACC001",
  "to": "ACC002",
  "amount": 10000,
  "currency": "MNT"
}
```

**Oracle**

```text
HTTP 201
{"result":"OK"}
```

## B3. Category-Partition ба PICT-ийн харьцуулалт

Category-Partition арга нь параметрийн сонголт, төлөөлөх утга, алдааны нөхцөл болон хязгаарлалтыг ойлгомжтой тодорхойлоход давуу талтай. Гараар боловсруулсан спецификацийн хүснэгт нь тест бүрийн хүлээгдэх үр дүнг тодорхой харуулдаг. PICT нь параметрийн хослолуудыг автоматаар үүсгэж, pairwise хамралтыг хангахад тохиромжтой. Гэхдээ PICT дангаараа бизнесийн дүрэм болон олон алдааны давуу эрэмбийг бүрэн тодорхойлохгүй. Хязгаарлалтгүй моделд нэг мөрөнд хэд хэдэн алдааны нөхцөл давхардаж болно. `IF` хязгаарлалт нь зөвшөөрөгдөх хослолыг удирддаг бол `~` сөрөг утгын тэмдэглэгээ нь алдааны нөхцөлүүдийг тусгаарлахад тусалдаг. Browser моделийн 2-way үр дүн 10 мөр, 3-way үр дүн 20 мөр байсан. Transfer моделийн гаралтад хязгаарлалтгүй болон `IF` хязгаарлалттай хувилбар 13 мөр, сөрөг утгатай хувилбар 16 мөр үүсгэсэн. Энэ лабораторийн хамгийн их бодол шаардсан хэсэг нь олон алдааны давуу эрэмбийг тогтоох, далд орчны нөхцөлүүдийг тодорхойлох, мөн PICT-ийн хослолуудыг бодит тестийн oracle болгон хувиргах ажил байлаа.

# Дүгнэлт

Энэ лабораторийн хүрээнд банкны шилжүүлгийн функцэд Category-Partition аргаар тестийн сонголт, төлөөлөх утга, хязгаарлалт болон спецификацийн хүснэгт боловсруулсан. Бүрэн олонлогийн 72 хослолоос хоёр `IF` хязгаарлалтын дараа 42 боломжит хослол үлдэхээр тооцоолсон. PICT ашиглан browser-ийн 2-way болон 3-way тестийн багцууд үүсгэсэн. Browser-ийн 2-way үр дүн 10 мөр байсан нь гараар гаргасан 9 мөрийн жишээнээс нэгээр олон байв. Transfer моделийн хязгаарлалтгүй болон `IF` хязгаарлалттай хувилбар тус бүр 13 мөр, сөрөг утгатай хувилбар 16 мөр гаргасан. Category-Partition нь алдааны утга, бизнесийн дүрэм болон хүлээгдэх үр дүнг тодорхойлоход илүү тохиромжтой. PICT нь параметрийн хослолуудыг автоматаар хамруулахад илүү тохиромжтой боловч greedy алгоритм хамгийн цөөн тестийн багцыг заавал гаргахгүй. Эдгээр хоёр аргыг хамтад нь ашиглах нь тестийн хамралтыг сайжруулж, алдааны нөхцөлийг илүү ойлгомжтой тодорхойлоход тусалдаг. Мөн `SINGLE` зарчмаар үлдэгдэл болон лимитийн хязгаарын утгуудыг тусгаарлан шалгаж, `~` тэмдэглэгээ нь `IF` хязгаарлалтыг орлохгүйг ялгаж тайлбарласан.
